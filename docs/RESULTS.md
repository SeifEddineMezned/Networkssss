# Measured TCP vs UDP results

Generated by `npm run bench:tcp` / `npm run bench:udp` (test/bench.js) on 2026-11-12 21:30 UTC.

Setup: real server process + 3 headless bot clients over real sockets on one machine (127.0.0.1), 15 s of play per profile, 30 Hz position stream per client, 1 reliable "shot" event per client per second. Impairments are injected by `server/common/simnet.js` on **every outgoing packet of the server and of every client** (so loss applies per hop: client->server and server->client). For TCP, a "lost" packet is modelled as a kernel retransmission (delay of RTO=200 ms, doubling, with head-of-line blocking of all later data), because TCP never exposes loss to the application.

## How to read it

- **Perceived lag (state age)** = time between a client sampling its position and another client receiving it. This is what a player sees as lag.
- **Freeze (gap)** = time between two consecutive position updates of the same remote player. Large values are visible stutter/teleport ("desync after a lost message").
- **State updates not delivered**: UDP drops lost ones on purpose, and the server's per-receiver batching (60 Hz) keeps only the newest state of each player, so an older one can be *superseded* (no retransmit; the next update 33 ms later supersedes it). TCP never loses them but delivers them late.
- **Reliable events** (shots, kills, scores, room ops) are never lost in either version: TCP by the kernel, UDP by our ACK/retransmit layer (server/common/reliable.js).
- **Disconnect detection**: a client freezes without closing its socket (half-open). TCP: app heartbeat 2 s / timeout 6 s. UDP: heartbeat 1 s / timeout 5 s. A *killed* TCP client is detected immediately (OS sends RST/FIN); UDP has no FIN, so it always relies on the heartbeat or an explicit BYE.
